# Research: sql.js Adapter Kysely Compatibility Issue

## Executive Summary

- **Root Cause Identified**: SqlJsStatementAdapter missing `readonly reader: boolean` property required by Kysely
- **Impact**: Kysely cannot determine if SQL statement is SELECT (reader) or INSERT/UPDATE/DELETE (writer)
- **Evidence**: Kysely's SqliteConnection checks `stmt.reader` before calling `stmt.all()` or `stmt.run()`
- **Solution**: Add `reader` property and `iterate()` method to SqlJsStatementAdapter
- **Verification**: Direct rawDb.prepare().run() works; Kysely queries fail (confirms interface mismatch)

## Critical Findings (Verified, Planner Attention Required)

### Finding 1: Missing `reader` Property

**Observation**: Kysely's SqliteStatement interface requires `readonly reader: boolean` property

**Evidence**: `node_modules/kysely/dist/esm/dialect/sqlite/sqlite-dialect-config.d.ts:31-42`

**Excerpt**:

```typescript
export interface SqliteStatement {
  readonly reader: boolean;
  all(parameters: ReadonlyArray<unknown>): unknown[];
  run(parameters: ReadonlyArray<unknown>): {
    changes: number | bigint;
    lastInsertRowid: number | bigint;
  };
  iterate(parameters: ReadonlyArray<unknown>): IterableIterator<unknown>;
}
```

**Direct consequence**: Without `reader` property, Kysely cannot determine which execution path to take

---

### Finding 2: Kysely Checks `reader` Before Execution

**Observation**: Kysely's SqliteConnection.executeQuery() uses `stmt.reader` to decide between `all()` and `run()`

**Evidence**: `node_modules/kysely/dist/esm/dialect/sqlite/sqlite-driver.js:58-73`

**Excerpt**:

```javascript
executeQuery(compiledQuery) {
    const { sql, parameters } = compiledQuery;
    const stmt = this.#db.prepare(sql);
    if (stmt.reader) {
        return Promise.resolve({
            rows: stmt.all(parameters),
        });
    }
    else {
        const { changes, lastInsertRowid } = stmt.run(parameters);
        const numAffectedRows = changes !== undefined && changes !== null ? BigInt(changes) : undefined;
        return Promise.resolve({
            numAffectedRows,
            insertId: lastInsertRowid !== undefined && lastInsertRowid !== null
                ? BigInt(lastInsertRowid)
                : undefined,
            rows: [],
        });
    }
}
```

**Direct consequence**: If `stmt.reader` is undefined, JavaScript's falsy check treats it as `false`, causing Kysely to always call `stmt.run()` even for SELECT queries

### Finding 3: better-sqlite3 Provides `reader` Property

**Evidence**: `node_modules/@types/better-sqlite3/index.d.ts:89-91`

**Excerpt**:

```typescript
interface Statement<BindParameters extends unknown[], Result = unknown> {
  database: Database;
  source: string;
  reader: boolean; // <-- Present in better-sqlite3
  readonly: boolean;
  busy: boolean;
  // ... methods

```

**Direct consequence**: Our adapter must implement this property to match better-sqlite3's interface

### Finding 4: Parameter Passing Works Correctly

**Observation**: better-sqlite3 accepts both REST parameters and array parameters

**Evidence**: better-sqlite3 official documentation (https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)

**Excerpt**:

```javascript
const stmt = db.prepare('INSERT INTO people VALUES (?, ?, ?)');

// The following are equivalent.
stmt.run('John', 'Smith', 45); // REST parameters
stmt.run(['John', 'Smith', 45]); // Array
stmt.run(['John'], ['Smith', 45]); // Mixed arrays
```

**Direct consequence**: Our flattening logic `params.length === 1 && Array.isArray(params[0]) ? params[0] : params` is correct and handles Kysely's array parameter passing

### Finding 5: Missing `iterate()` Method

**Observation**: Kysely's SqliteStatement interface requires `iterate()` method for streaming queries

**Evidence**: `node_modules/kysely/dist/esm/dialect/sqlite/sqlite-dialect-config.d.ts:40`

**Excerpt**:

```typescript
export interface SqliteStatement {
  readonly reader: boolean;
  all(parameters: ReadonlyArray<unknown>): unknown[];
  run(parameters: ReadonlyArray<unknown>): { changes; lastInsertRowid };
  iterate(parameters: ReadonlyArray<unknown>): IterableIterator<unknown>; // <-- Missing in our adapter
}
```

**Direct consequence**: If Kysely attempts to use streaming queries, it will fail with "iterate is not a function"

## Detailed Technical Analysis (Verified)

### Interface Mismatch: Our Adapter vs. Kysely's Expectations

**Our Current Interface** (`src/main/database/client.ts:22-43`):

```typescript
export interface Statement {
  run(...params: unknown[]): RunResult;
  get(...params: unknown[]): unknown;
  all(...params: unknown[]): unknown[];
}
```

**Kysely's Expected Interface** (`node_modules/kysely/dist/esm/dialect/sqlite/sqlite-dialect-config.d.ts:31-42`):

```typescript
export interface SqliteStatement {
  readonly reader: boolean;
  all(parameters: ReadonlyArray<unknown>): unknown[];
  run(parameters: ReadonlyArray<unknown>): {
    changes: number | bigint;
    lastInsertRowid: number | bigint;
  };
  iterate(parameters: ReadonlyArray<unknown>): IterableIterator<unknown>;
}
```

**Differences**:

1. **Missing `reader` property** - Critical for Kysely's execution path decision
2. **Missing `iterate()` method** - Required for streaming queries
3. **Has `get()` method** - Not used by Kysely (Kysely uses `all()` and takes first)
4. **Parameter signatures** - REST vs. array (but better-sqlite3 accepts both, so this works)

---

### Why Direct rawDb Calls Work But Kysely Queries Fail

**Direct rawDb.prepare().run()** (`src/main/database/migrations.ts:105-112`):

```typescript
rawDb
  .prepare(
    `INSERT INTO dietary_profile (id, hard_restrictions, updated_at) 
           VALUES (?, ?, ?)`
  )
  .run(1, '["gluten-free", "lactose-free"]', new Date().toISOString());
```

- **Works because**: Calls our `run()` method directly with REST parameters
- **No dependency on**: `reader` property (not checked)
- **Result**: INSERT succeeds, row is created

**Kysely Query** (`src/main/database/dal/dietary-profile.ts:8-12`):

```typescript
const row = await db
  .selectFrom('dietary_profile')
  .selectAll()
  .where('id', '=', 1)
  .executeTakeFirst();
```

- **Fails because**: Kysely checks `stmt.reader` to decide execution path
- **Current behavior**: `stmt.reader` is undefined → treated as `false` → calls `stmt.run()` instead of `stmt.all()`
- **Result**: SELECT query executed as if it were an INSERT/UPDATE, returns empty rows

---

### How sql.js Determines Reader vs. Writer

**sql.js Statement API** (from sql.js documentation):

```javascript
const stmt = db.prepare(sql);
console.log(stmt.getColumnNames()); // Returns [] for non-SELECT, column names for SELECT
```

**Detection Strategy**:

1. **Option A**: Parse SQL to detect SELECT keyword (fragile, doesn't handle CTEs)
2. **Option B**: Use sql.js's `stmt.getColumnNames()` - returns empty array for non-SELECT
3. **Option C**: Try to step() and check if there are columns (requires execution)

**Recommended**: Option B - `reader = stmt.getColumnNames().length > 0`

## Recommended Fix

**Add to SqlJsStatementAdapter**:

1. **`reader` property**:

   ```typescript
   class SqlJsStatementAdapter implements Statement {
     readonly reader: boolean;

     constructor(
       private db: Database,
       private sql: string
     ) {
       const stmt = db.prepare(sql);
       this.reader = stmt.getColumnNames().length > 0;
       stmt.free();
     }
   }
   ```

2. **`iterate()` method**:

   ```typescript
   *iterate(params: unknown[]): IterableIterator<unknown> {
     const stmt = this.db.prepare(this.sql);
     try {
       if (params.length > 0) {
         const bindParams = params.length === 1 && Array.isArray(params[0]) ? params[0] : params;
         stmt.bind(bindParams);
       }
       while (stmt.step()) {
         yield stmt.getAsObject();
       }
     } finally {
       stmt.free();
     }
   }
   ```

3. **Update method signatures** to match Kysely's expectations (accept array parameter instead of REST):
   ```typescript
   run(params: unknown[]): RunResult { ... }
   all(params: unknown[]): unknown[] { ... }
   ```
