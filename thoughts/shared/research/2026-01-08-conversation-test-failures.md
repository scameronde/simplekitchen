# Research: E2E Test Failures in conversation-suggestions.spec.ts

## Executive Summary
- Both E2E tests in `conversation-suggestions.spec.ts` are failing due to reliance on live OpenAI API responses and incorrect test assumptions about UI state.
- Test 1 (`should display recipe suggestions after conversation`) fails because it expects specific AI response text ("time do you have") that may not be generated by the actual OpenAI API.
- Test 2 (`should continue conversation if AI needs more info`) fails because it expects 1 AI message bubble with class `bg-gray-200` but receives 4 elements with this class.
- The root cause is that `.bg-gray-200` is used for multiple UI elements: AI message bubbles, loading indicators, and button backgrounds.
- No mock AI implementation exists for E2E tests; the application uses real OpenAI API calls even when `E2E_TEST=true`.
- The tests are non-deterministic because they depend on live AI responses which can vary.

## Detailed Technical Analysis (Verified)

### Conversation Flow Architecture

1. **Session Initialization** (`src/main/conversation/session-manager.ts:23-40`)
   - User clicks "What's for dinner?" → Frontend calls `conversationAPI.startSession()`
   - Backend creates empty session with `messages: []`
   - No initial AI greeting is sent

2. **User Message Handling** (`src/renderer/pages/ConversationPage.tsx:196-254`)
   - User types message → Frontend dispatches `add_user_message` action
   - Frontend calls `conversationAPI.sendMessage(sessionId, messageContent)`
   - Backend processes message through OpenAI API

3. **AI Response Processing** (`src/main/conversation/conversation-service.ts:64-132`)
   - Backend calls OpenAI with conversation history and system prompt
   - OpenAI returns structured response: `{ aiMessage, extractedContext, shouldTransition }`
   - If `shouldTransition=true`, backend stores transition message for later use
   - Frontend receives AI message and displays it

4. **Transition to Suggestions** (when `shouldTransition=true`)
   - Frontend calls `conversationAPI.getSuggestions(sessionId)`
   - Backend retrieves stored transition message
   - Backend ranks recipes using second OpenAI call
   - Frontend displays transition message + recipe suggestion cards

### UI Rendering Logic

**Message Display** (`src/renderer/pages/ConversationPage.tsx:319-380`)
- All messages in `state.messages` are rendered in a loop
- User messages: `bg-blue-500 text-white`
- AI messages: `bg-gray-200 text-gray-900`
- If message has `suggestions` property, RecipeSuggestionCard components are rendered below the message
- Loading state shows separate `bg-gray-200` div with "AI is thinking..." text

**State Management** (`src/renderer/pages/ConversationPage.tsx:51-126`)
- Uses `useReducer` with `ConversationState`
- Initial state: `messages: []`, `isLoading: false`, `sessionId: null`
- Actions: `add_user_message`, `add_ai_message`, `add_ai_message_with_suggestions`, `set_loading`

### Finding 6: Fallback Response Triggered Without API Key

**Observation:** When `OPENAI_API_KEY` is missing, `getOpenAIClient()` throws an error, which is caught by the error handler in `processConversationTurn()`. This returns a fallback response with `shouldTransition: true`.

**Direct consequence:** 
- Test 1 expects text matching `/time do you have/i` but receives: "Sorry, I'm having trouble right now. Let's move forward with default settings."
- The frontend then calls `getSuggestions()` which also fails, likely showing an error instead of recipe cards.

**Evidence:** `src/main/conversation/conversation-service.ts:29-43` (API key check)

## Final Root Cause Analysis

### Primary Root Cause
**Conversation handlers lack E2E mock implementation**, causing tests to use real OpenAI API which:
1. Requires API key in environment (currently missing)
2. Returns non-deterministic responses (breaks text matching assertions)
3. Incurs API costs and latency
4. Fails in CI/CD environments without API key

### Secondary Issues
1. **Missing API key in E2E environment** - `.env` file not loaded when `E2E_TEST=true`
2. **Brittle text assertions** - Tests expect exact AI response text (e.g., `/time do you have/i`)
3. **Overly broad CSS selectors** - `.bg-gray-200` matches multiple UI elements

### Solution Alignment with Existing Patterns
The conversation feature should follow the **exact same pattern** as AI recipe generation and recipe import:
1. Create `conversation-handlers.mock.ts` with deterministic mock responses
2. Add `isE2ETest()` check in conversation IPC handlers
3. Use test signals for error scenarios (e.g., sending "MOCK_ERROR" triggers specific errors)
4. Return deterministic conversation flows that match test expectations
